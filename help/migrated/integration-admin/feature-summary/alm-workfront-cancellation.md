# ALM-Workfrontのキャンセル/アップデートトリガー

## 概要

Adobe Learning Manager(Learning Manager)では、Workfrontで行われた変更に基づいて、インストラクター主導およびバーチャルインストラクター主導(ILT/VILT)のセッションをキャンセルして再アクティベートできるようになりました。 WorkfrontからLearning Managerへの移行を通じて、WorkfrontでスケジュールしたセッションをLearning Managerに読み込む場合は、移行データで各セッションのステータスを「アクティブ」または「キャンセル」に設定することができます。 その後、管理者がユーザーインターフェイスでセッションをキャンセルしたかのように、Learning Managerは変更を適用します。

移行でセッションをキャンセルすると、Learning Managerのユーザーインターフェイスでセッションをキャンセルした場合と同じ動作をします。 1つの故意の違いは再アクティブ化です。再アクティブ化の詳細については、「[キャンセルされたセッションを再アクティブ化する](#reactivate-a-cancelled-session)」を参照してください。

### 要件

日時、インストラクター、場所やリンク、処理能力などのセッションの更新は、WorkfrontからLearning Managerに移行によってすでに反映されています。 キャンセルできませんでした。 Workfrontでセッションがキャンセルされたときに、Learning Managerで通知できませんでした。次の問題が発生しました。

* 学習者がセッションに登録したままになるとセッションが終了し、混乱が発生して番組が表示されなくなりました。
* 管理者は、Learning Managerで手動でキャンセルを繰り返す必要がありました。
* WorkfrontとLearning Managerの同期が取れなくなり、スケジュールを設定する際の信頼できる情報源としてのWorkfrontが弱体化しました。

### 動作の仕組み

1. 配信管理者がWorkfrontのセッションをキャンセルします。
1. 移行データのセッション行には、Cancelledに設定された新しいセッション・ステート列が含まれます。
1. システム管理者は、APIを介して移行を実行します。
1. Learning Managerは、一致したセッションをキャンセル済みとしてマークし、ユーザーインターフェイスからキャンセルが送信するのと同じ通知を送信します。

>[!NOTE]
>
>この機能は、2番目のリアルタイム統合パスを追加するのではなく、既存の移行プロセスを拡張します。

## ユースケース

Workfrontで開始する解約には、次の役割が関係します。

### 関与するロール

| 役割 | 概要 |
|---|---|
| 配信マネージャー | セッションのキャンセルなど、Workfrontのトレーニングカレンダーをスケジュールして管理します。 配信マネージャーはLearning Managerユーザーインターフェイスを使用しません。 キャンセルがLearning Managerに到達する唯一のパスは移行です。 |
| システム管理者 | APIを介して移行を実行します。 WorkfrontとLearning Managerの間のパイプラインを通り、デリバリーマネージャーやLearning Manager管理者とは別に作業を行います。 |
| 管理者 | Learning Managerユーザーインターフェイスでコースおよびセッションデータを管理します。 Workfrontの変更を通知された後、管理者がセッションを手動でキャンセルする必要がなくなりました。 |
| 作成者 | Learning Managerユーザーインターフェイスのコースおよびセッションコンテンツを所有します。 |
| 学習プログラム / 資格認定を | セッションに割り当てられている。 インストラクターは正しいセッション状態を確認し、インストラクターが指示するセッションがキャンセルされると通知されます。 |
| 学習者 | Learning Managerを介してセッションに登録されている。 セッションがキャンセルされると、学習者にはすぐに通知されます。 |

### 一般的なシナリオ

| シナリオ | お客様の対応 | 結果 |
|---|---|---|
| リソースが利用できない、ベンダーに問題があるなど、Workfrontでセッションがキャンセルされる。 | セッションの移行行でセッション・ステートを「 Cancelled 」に設定し、移行を実行します。 | Learning Managerでセッションがキャンセルされ、影響を受けたユーザーに通知されます。 |
| Workfrontでアクティブなセッションの詳細が変わります。 | 変更した値を移行の行に含めます。 セッションステートをアクティブに設定するか、空白のままにします。 | セッションが更新されます。 Learning Managerからセッションの更新情報がメールで送信されます。 |
| キャンセルされたセッションは、Workfrontで再開されます。 | 移行の行のセッション・ステートを「 Active 」に設定し、移行を実行します。 | セッションがアクティブになり、変更およびキャンセルが可能になります。 |
| 状態をアクティブに設定せずに、キャンセルされたセッションの更新された詳細が送信されます。 | ユーザーがアクションを実行する必要はありません。 | セッションはキャンセルされたままで、行は検証エラーを返し、詳細は変更されません。 |
| 移行行には、セッション状態は含まれません。 | この列は、空白のままにするか省略します。 | Learning Managerのセッションの現在の状態は変更されないままになります。 |

## 主な機能

* **セッション状態列。** 移行スキーマには、アクティブおよびキャンセル済みをサポートするオプションのセッション状態フィールドが含まれています。
* **移行による解約。** 行の状態がCancelledの場合、Learning Managerの一致するセッションはキャンセルされます。 Learning Managerでは、移行でセッションの作成や更新に既に使用されているものと同じマッチングキーが使用されます。
* **Learning Managerで手動で作業することはできません。** 管理者は、ユーザーインターフェイスでセッションを再度キャンセルする必要はありません。
* **ユーザーインターフェイスでキャンセルするのと同じ動作です。** 登録処理、学習者向けの表示、レポート、監査追跡、通知は、ユーザーインターフェイスからのキャンセルに一致します。
* **ライセンス認証の再開** 移行データで状態を明示的に設定することで、キャンセルされたセッションをアクティブに戻すことができます。
* **キャンセルされたセッションの保護。** 行が明示的に状態をアクティブに設定しない限り、移行によってキャンセルされたセッションの詳細は変更されません。
* **下位互換性** 状態列はオプションであるため、既存の移行ファイルは変更されることなく引き続き機能します。
* **通知の完了** 学習者、インストラクター、管理者、作成者、マネージャーは、ユーザーインターフェイスから解約と同じ電子メールを受け取ります。

## セッションの状態

Learning Managerのすべてのセッションは、2つの状態のいずれかになります。

| ステート | 意味 |
|---|---|
| アクティブ | デフォルトのステート。 このセッションはライブで行われ、学習者はセッションに登録して参加できます。 |
| キャンセル済み | セッションがキャンセルされます。 登録された学習者、管理者、作成者、マネージャーには、ユーザーインターフェイスからのキャンセルに関する通知と同様の通知が届きます。 |

### 移行の状態遷移ルール

次の表は、マイグレーション行が処理されるときの動作を示しています。 Learning Managerでは、移行で作成および更新に既に使用されている一致キーを使用してセッションを識別します。

| Learning Managerの現在の状態 | 移行行のセッション状態 | 結果 |
|---|---|---|
| セッションが存在しません | アクティブまたは空白 | セッションがアクティブとして作成されます。 |
| アクティブ | アクティブまたは空白 | セッションはアクティブなままです。 行で変更された値が適用されます。 |
| アクティブ | キャンセル済み | セッションがキャンセルされ、通知が送信されます。 |
| キャンセル済み | キャンセル済み | 行がスキップされます。 キャンセル済みのセッションを再度キャンセルすることはできません。 |
| キャンセル済み | アクティブ | セッションが再アクティベートされます。 行で変更された値が適用されます。 |
| キャンセル済み | 空白 | セッションはキャンセルされたままになります。 行の値が変更されている場合は、検証エラーが返され、詳細は変更されません。 |

### セッション・ステート列のルール

* この列は、すべての行でオプションです。
* 列が空の場合、セッションはアクティブに更新されます。
* 列に明示的に「アクティブ」と表示されている場合にのみ、移行を通じてセッションが再びアクティブになります。

セッション・ステート列で次のいずれかの値を使用します。

* `state = Active`
* `state = Cancelled`

>[!NOTE]
>
>正確な列ヘッダーと受け入れられる値が確認されています。 移行ドキュメントで指定されている名前を使用します。

## キャンセルされたセッションの更新

移行によってキャンセルされたセッションの詳細を更新することはできません。 キャンセルされたセッションの行に変更された値が含まれていて、状態がActiveに設定されていない場合、Learning Managerは検証エラーを返し、セッションをキャンセルしたままにします。変更された詳細の適用も保存もされません。 Learning Managerでは、セッションのアップデートを促す電子メールは送信されません。

### 移行を使用したセッションのキャンセル

Workfrontでセッションがキャンセルされ、Learning Managerに変更内容を反映させる場合は、次の手順に従います。

**始める前に**

* このセッションはLearning Managerに既に存在し、WorkfrontからLearning Managerへの移行を通じて読み込まれます。
* セッションを識別するために移行で使用する一致キーがわかります。

1. **Workfront**&#x200B;で、セッションをキャンセルします。
1. 移行に使用するセッションCSVファイルで、セッションの行を検索します。 一致するキーが、セッションの作成時に使用したキーと同じであることを確認してください。
1. セッション状態の列に、**キャンセル済み**&#x200B;と入力します。
1. APIを介して移行を実行します。
1. Learning Managerでセッションがキャンセルされていることを確認します。

Learning Managerはセッションをキャンセル済みとしてマークし、登録された学習者をユーザーインターフェイスからキャンセルする場合と同様に処理して、キャンセル通知を送信します。 Learning Managerユーザーインターフェイスにアクションは必要ありません。

>[!NOTE]
>
>セッションが既にキャンセルされている場合、Learning Managerはその行をスキップします。

### アクティブなセッションの更新

アクティブなセッションでは、既存の移行の更新動作は引き続き使用できます。 セッション・ステートを「アクティブ」に設定するか、空白のままにし、変更した値を行に含めます。 移行パイプラインを通じて、引き続き日付と時刻、インストラクター、場所やリンク、容量などの詳細を更新できます。

「アクティブ」を選択すると、既存の作成および更新動作が維持されます。 キャンセル済み：セッションCSVの移行により、ユーザーインターフェイスで提供されるのと同じセッションのキャンセルを呼び出します。

### キャンセルされたセッションの再開

取り消されたセッションは、状態を明示的にアクティブに設定した場合にのみ、アクティブな状態に戻ります。 セッションを再アクティベートするには、移行を使用するか、ユーザーインターフェイスでセッションを編集します。

1. セッションCSVファイルで、キャンセルされたセッションの行を探します。 一致するキーが、セッションの作成時に使用したキーと同じであることを確認してください。
1. セッション状態の列に、 Activeと入力します。
1. （オプション）変更する行のその他の値（日時、インストラクター、場所またはリンク、容量など）を更新します。
1. APIを介して移行を実行します。

セッションがアクティブになり、その詳細を変更できます。 移行またはユーザーインターフェイスを介して再アクティブ化されたセッションは、いずれかのパスで再びキャンセルできます。

>[!IMPORTANT]
>
>状態をActiveに設定せずに、キャンセルされたセッションに対して更新されたセッションの詳細を送信した場合、セッションはキャンセルされたままになり、行は検証エラーを返します。

## 通知

移行によりセッションがキャンセルされた場合、Learning Managerはユーザーインターフェイスからキャンセル用に送信するすべての電子メールを送信します。 受信者の適用範囲は縮小されず、コンテンツでは同じテンプレートが使用されるため、受信者は解約がどのように開始されたかを知ることができません。

セッションに適用できる受信者は次のとおりです。

| 受信者 | 通知 |
|---|---|
| 学習者 | セッションに登録した学習者には、セッションがキャンセルされたことが通知されます。 |
| インストラクタ | セッションに割り当てられたインストラクターには、キャンセルの通知が送信されます。 |
| マネージャー | マネージャーはキャンセル通知を受け取ります。 |

### キャンセルされたセッションの電子メール

キャンセルされたセッションでは、セッション更新メールは生成されません。 セッションがキャンセルされている間、日時、インストラクター、場所またはリンク、容量を変更しても、セッションの更新メールは送信されません。 キャンセル済みのセッションには、キャンセルと再アクティベーションの通知のみが適用されます。

## 考慮事項と制限

* この機能では移行を使用するため、Workfrontで行ったキャンセルは、移行の実行時にLearning Managerに通知されます。 Webhookベースのリアルタイムのキャンセルはサポートされていません。
* 移行で、キャンセルされたセッションの詳細を変更することはできません。 これを変更するには、まず状態を「アクティブ」に設定します。
* セッション状態列はオプションです。 これを省略した行は、セッションの状態を変更しません。
* この機能は、既存の移行統合を拡張します。 2番目のリアルタイム統合パスは追加されません。
* 移行スケジュールまたはトリガーは、組織が移行スケジュールまたはトリガーを実行するために使用するツールによって異なります。 このガイドでは、固定スケジュールは定義されていません。
* 配信マネージャーはWorkfrontでのみ動作します。 セッションをキャンセルするのに、Learning Managerユーザーインターフェイスにアクセスする必要はありません。

## 成功の手段

| 測定する | Target |
|---|---|
| 管理者またはカスタマーサポートが手動で複製するキャンセル | 起動後の1つの完全なリリースサイクルで0に低下します。 |
| WorkfrontのキャンセルがLearning Managerに反映される | 100%のキャンセルイベントが1つの移行サイクル内で処理されます。 |
| ユーザーインターフェイスと移行のキャンセル間の通知の一致 | 受信者の範囲（管理者、作成者、マネージャー、学習者）に0のギャップ、およびキャンセルされたセッションに対する不要な更新メールに0のギャップがあります。 |

## トラブルシューティング

| 問題 | 予想される原因または考えられる原因 | アクション |
|---|---|---|
| Workfrontでキャンセルされた後も、セッションはアクティブのままです。 | 移行がまだキャンセルを処理していないか、移行の行に明示的なキャンセル済みの状態が含まれていません。 | マイグレーション入力と処理結果を確認します。 |
| キャンセルされたセッションの詳細は変更されません。 | セッションがキャンセルされたままの間の予期された動作です。 | ステートをアクティブに設定してセッションを再アクティベートしてから、変更を適用します。 |
| キャンセルされたセッションには、セッションの更新後の電子メールが送信されません。 | 予期された動作です。 キャンセルされたセッションでは、通常のアップデート電子メールが抑制されます。 | 詳細情報のみの更新ではなく、解約と再アクティベーションのライフサイクルを使用します。 |
| 取り消し行はスキップされます。 | Learning Managerの一致するセッションは既にキャンセルされています。 | 解約の必要はありません。 アクティブに戻る必要がある場合は、最初にセッションを再アクティブ化します。 |
| 受信者は、ユーザーインターフェイスの取り消しと同じ取り消し電子メールを受信しました。 | 予期された動作です。 移行のキャンセルは、ユーザーインターフェイスに合わせて設計されています。 | 対応は不要です。 |
| セッション状態が空白の場合、動作は不明です。 | ソース要件は、空白ステートの処理で競合します。 | トランジションが空白の状態になる前に、リリースの動作を確認してください。 |
